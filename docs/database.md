# PostgreSQL database

All seven domain tables use UUID primary keys. Times are timezone-aware. PostgreSQL enums, JSONB payloads, indexes, uniqueness and foreign keys enforce invariants. `alembic_version` records schema revision.

| Table | Purpose and relationships |
| --- | --- |
| `users` | Unique indexed WhatsApp user ID, optional phone/display name, first/last-seen and audit timestamps. Parent of profiles, crops, conversations. |
| `farmer_profiles` | One optional profile per user; language, state, district, village, farm size/unit, soil and irrigation. No field is required to chat. |
| `farmer_crops` | Many crop records per user with name, variety, season, sowing date, area/unit and status. Optional unique source-message FK prevents repeated command processing from creating duplicate crops. |
| `conversations` | Active/closed conversation, user FK, start/last-message/audit timestamps. Partial unique index permits at most one active conversation per user. |
| `messages` | Inbound/outbound content and metadata, role/type/status, provider ID, delivery/error timestamps. Conversation/user FKs. Unique provider ID; unique reply-to FK ensures one saved assistant reply per inbound. BIGINT identity sequence supplies stable order alongside UUID identity. `provider_timestamp` supports reply-window checking. `send_started_at` records committed send intent. |
| `webhook_events` | Unique deterministic event key, full raw envelope or per-event JSONB, processing state/error and receipt time. Indexed provider ID supports delayed receipt reconciliation. |
| `processing_jobs` | Unique inbound-message FK; conversation FK and inbound sequence; job type/status, attempts/max, available-at, owner/lock time, safe failure code, completed/audit times. Poll and conversation-order indexes support distributed workers. |

Enums: `ConversationStatus`, `MessageDirection`, `MessageRole`, `MessageType`, `MessageStatus`, `ProcessingJobStatus`, `FarmerCropStatus`. Constraints reject negative farm/crop areas and invalid attempt counters. UUIDs are generated by the application. Direct SQL writers must supply required values/defaults just as the ORM does.

The initial Alembic migration creates all tables/enums/indexes, then explicitly adds the crop source-message FK once `messages` exists. Downgrade removes the FK before tables and drops enum types. Always inspect autogenerated migrations: enum changes, partial indexes, deferred FKs and data transformations may need manual SQL.

```bat
python -m alembic upgrade head
python -m alembic check
python -m alembic revision --autogenerate -m "add field"
```

## Privacy and deletion

User-linked records use cascade deletion; the crop source-message reference becomes null when appropriate. Raw audit envelopes can include multiple users and are not covered by deleting one user row. Any retention/erasure implementation must therefore also redact or expire matching `webhook_events` payloads and account for backups. Automatic deletion is intentionally not enabled. Keep the application database private, encrypt storage/backups, and test restores.

## Operational queries

```sql
SELECT status, count(*), min(available_at) FROM processing_jobs GROUP BY status;
SELECT id, message_id, attempts, last_error, locked_at FROM processing_jobs
WHERE status IN ('FAILED', 'PROCESSING') ORDER BY created_at;
SELECT count(*) FROM webhook_events WHERE event_type='status' AND NOT processed;
```

These belong in a trusted operator console. There is no public SQL/admin endpoint.
